# Sync Protocol v1

* 状态：Accepted for MVP
* 日期：2026-08-03

## Endpoints

```http
POST /v1/books/{bookId}/sync/push
GET  /v1/books/{bookId}/sync/pull?cursor={n}&limit={n}
POST /v1/books/{bookId}/sync/bootstrap
```

WebSocket（后续）：`{"type":"sync.available","bookId","cursor"}` — 仅唤醒。

## Push

Request:

```json
{
  "deviceId": "dev_01",
  "mutations": [
    {
      "mutationId": "0198...",
      "entityType": "transaction",
      "entityId": "0198...",
      "operation": "create",
      "baseVersion": 0,
      "schemaVersion": 1,
      "payload": {
        "description": "Lunch",
        "entries": [
          {"accountId": "acc_food", "amountMinor": "2500", "currency": "CNY"},
          {"accountId": "acc_cash", "amountMinor": "-2500", "currency": "CNY"}
        ]
      }
    }
  ]
}
```

分类也是账本账户，使用同一 Mutation 通道同步。客户端新增分类使用
`entityType=account`、`operation=create`，编辑分类使用 `operation=update`：

```json
{
  "entityType": "account",
  "entityId": "{bookId}:category_meals",
  "operation": "create",
  "baseVersion": 0,
  "schemaVersion": 1,
  "payload": {
    "name": "Meals",
    "accountType": "expense",
    "currency": "CNY",
    "parentAccountId": "{bookId}:acc_food"
  }
}
```

`entityId` 必须属于当前账本，`accountType` 支持 `income` 或 `expense`（以及
服务端已有的其他账户类型），名称会去除首尾空白并限制为 24 个字符。服务端
将分类变更写入 `sync_changes`，客户端 Pull/Bootstrap 时按账本 ID 重写本地
账户 ID，因此交易可以在分类 Mutation 之后引用新分类。

`parentAccountId` 是可选的两级分类字段。非空时只允许用于 `income` 或
`expense` Account，并且必须指向当前账本、同一 `accountType` 的一级分类。
父分类不能是自身或二级分类；已有子分类的一级分类也不能改为二级分类。字段
类型或账本作用域格式无效时返回 `INVALID_PAYLOAD`；父级不存在、跨类型、自引
用或会形成第三级时返回 `INVALID_CATEGORY_PARENT`。两者都是永久拒绝。

为兼容不认识分类层级的旧客户端，Push Request 必须区分字段缺省和 JSON
`null`：

| `parentAccountId` 状态 | `create` | `update` |
|------------------------|----------|----------|
| 字段缺省 | 创建一级分类 | 保留当前父分类 |
| 显式 `null` | 创建一级分类 | 提升为一级分类 |
| 当前账本中的 AccountId | 创建二级分类 | 设置或更换父分类 |

旧客户端更新二级分类时不会发送该字段，因此只会修改它认识的字段，不会意外
把分类提升为一级。服务端写入 Change Log 的 canonical account payload，以及
Pull 和 Bootstrap 返回的 Account，都始终包含 `parentAccountId`；一级分类的值
为 `null`。客户端在本地账本 ID 与远端账本 ID 之间转换时，必须同时重写
`entityId`、交易中的 `accountId` 和非空 `parentAccountId`。

客户端收到 `INVALID_CATEGORY_PARENT` 时，不把 Account Mutation 放入仅支持交易
语义的通用冲突队列。客户端将本地分类提升为一级，使用新的 `mutationId` 生成
等价 Mutation，并在本次同步中最多重试一次。不能复用原 `mutationId`，因为服
务端会按幂等键返回第一次的永久拒绝 Receipt。Pull 中的 `parentAccountId` 若
既不是字符串也不是 `null`，客户端必须中止该批 Pull，且不得推进 cursor。

默认分类使用稳定的账本作用域 AccountId。客户端初始化或本地数据库升级只
插入缺失项，不覆盖用户修改；服务端数据库升级和运行时创建/补齐 Book 也幂等
补齐，并仅为实际插入的默认 Account 写入 `sync_changes`。因此在线设备可通过
Pull 收到补齐项，Bootstrap 客户端则直接获得完整集合。

Rules:

- Batch 非大事务；每 Mutation 独立处理。
- 幂等键：`(bookId, deviceId, mutationId)` → 返回原 Receipt。
- 永久拒绝不阻止后续 Mutation。
- 业务数据 + Change Log + Receipt 原子（PG 模式）；内存模式等价顺序写。
- PG 模式按 Book 串行执行 Account 层级校验与写入，避免并发移动形成循环或第三级。

Response:

```json
{
  "receipts": [
    {
      "mutationId": "0198...",
      "status": "applied|rejected",
      "resultCode": "OK|LEDGER_UNBALANCED|LEDGER_VERSION_CONFLICT|...",
      "entityVersion": 1
    }
  ]
}
```

## Pull

- `sequence > cursor`，正序。
- 默认 limit 500，最大 1000。
- 同一 `commitId` 不得跨页拆开。
- `nextCursor` = 本页最大 sequence。

## Bootstrap

1. 记录高水位 cursor。
2. 分页导出实体。
3. 客户端导入后从高水位 Pull。

Cursor 过期：

```json
{
  "code": "SYNC_CURSOR_EXPIRED",
  "bootstrapRequired": true
}
```

## 错误码（客户端只依赖 code）

| code | 含义 |
|------|------|
| OK | 成功 |
| INVALID_PAYLOAD | Payload 字段、类型或账本作用域无效 |
| LEDGER_UNBALANCED | 复式不平衡 |
| LEDGER_VERSION_CONFLICT | 版本冲突 |
| INVALID_CATEGORY_PARENT | 分类父级无效或会形成第三级 |
| SYNC_CURSOR_EXPIRED | 需 Bootstrap |
| UNSUPPORTED_MUTATION | 暂不支持的操作 |

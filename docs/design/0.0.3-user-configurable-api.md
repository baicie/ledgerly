# User-configurable API endpoint for 0.0.3

* Branch: `codex/user-configurable-api-0.0.3`
* Target: `v0.0.3`
* Status: Ready for release

## Goal

Allow each Ledgerly installation to choose and persist the API origin it
connects to. A release client must remain usable when no API origin was
embedded at build time, while preserving the production transport rules and
preventing authentication state from crossing server boundaries.

## Product contract

* A release build with no saved or embedded endpoint opens an API setup screen.
* A saved endpoint takes precedence over the optional
  `LEDGERLY_API_BASE_URL` build default.
* Release builds accept only non-loopback HTTPS origins. Debug builds may use
  HTTP and loopback origins for local development.
* Origins cannot contain credentials, a non-root path, query, or fragment.
* Signed-out users can edit the endpoint from the authentication screen.
* If session restoration fails, the startup error screen shows the active
  origin and lets the user replace it before retrying.
* Signed-in users can edit it from Settings after an explicit confirmation.
* Switching while signed in validates the new origin first, logs out from the
  old origin second, and persists the new origin last.
* A successful switch replaces the endpoint-keyed Riverpod scope so the old
  router, Dio clients, authentication repository, session store, sync service,
  and database handles are disposed before new endpoint-bound instances are
  used.
* A failed validation or persistence operation leaves the active endpoint
  unchanged. A failed remote logout still clears local authentication before
  the endpoint is saved.

## Persistence and security

The selected origin is non-secret configuration and is persisted by a small
platform store. Native platforms use application preferences and Web uses
browser local storage. The store contains only the normalized origin.

Device IDs, native refresh tokens, and the Web signed-out marker use versioned
keys namespaced by the normalized API origin. Consequently:

* a native refresh token issued by one origin is never sent to another;
* a Web logout marker for one origin does not suppress restore for another;
* a device identifier is stable for one installation and origin, but cannot
  correlate that installation across independently operated servers; and
* legacy unscoped authentication keys are ignored rather than migrated.

Browser refresh cookies remain `HttpOnly` and are isolated by the browser's
cookie origin rules. JavaScript does not read or copy them during a switch.

## Startup state model

1. Load the saved endpoint.
2. If none exists, inspect the optional embedded build default.
3. If a candidate exists, validate and normalize it under the current build
   policy.
4. If no candidate exists in release, show endpoint setup. Debug retains its
   local development fallback.
5. Once ready, mount an endpoint-keyed application scope and restore only that
   origin's authentication session.
6. If restoration fails, keep the active origin editable on the startup error
   screen so an offline or incorrect service does not trap the installation.

An invalid saved value is shown as a configuration error on the setup screen;
the client does not silently fall back to another server.

## Release workflow

`LEDGERLY_API_BASE_URL` is an optional repository variable that supplies an
initial default. The Release workflow must also build successfully when it is
empty. It must never substitute documentation example domains. Client version
is `0.0.3+3`, the release tag is `v0.0.3`, and a tag-triggered release does not
deploy the server automatically.

## Acceptance criteria

* Unit tests cover missing release configuration, persisted/default
  precedence, normalization, invalid release origins, persistence failures,
  and restart recovery.
* Session-store tests prove device IDs, native refresh tokens, and Web logout
  markers are isolated between two API origins.
* Widget tests prove first-run setup, startup-failure recovery,
  authentication-page editing, and the signed-in switch order (`logout`
  before endpoint persistence).
* Existing authentication, routing, sync, migration, and UI tests continue to
  pass.
* Flutter formatting, static analysis, tests, Web release build without a Dart
  define, and the repository's server checks pass.
* The pull request is squash-merged into `main`; `v0.0.3` points at that merge.
* The GitHub Release contains the Web archive and all three signed Android APKs,
  and GHCR exposes the `v0.0.3` server image.
* The temporary feature worktree and local feature branch are removed after
  release verification.

## Rollback

The endpoint key is additive and the authentication key version changes only
local client storage. Rolling back the server image is independent. A client
rollback may require users to enter their endpoint again and sign in; no
refresh token is migrated back to the legacy global key.
